ARXO-2026-0641 · Reported

Gloas fork choice and honest validator rules do not cover Fulu blocks and Fulu store entries at the fork

Issue 5096 and the open pull request 5125 cover one place where Gloas fork choice reads the bid field of a Fulu parent block. The text has further places of this kind. The finalized and safe execution block hashes for the execution layer are read from the bid field of blocks that stay Fulu blocks for at least two epochs after the fork. Bid gossip ignores every bid for the fork slot, because only envelopes fill the list of known payloads and the last Fulu payload never arrives in an envelope. Fork choice gives a Fulu head only an EMPTY child, since a Fulu block never has an envelope, so the honest validator guide tells the proposer of the initial Gloas block to use the parent hash of the last Fulu payload, while the state transition requires the hash of that payload itself. The fork-choice store has no conversion at the fork, although the types of block timeliness and latest messages change in Gloas.

Consequence

Minimal preset, fork at epoch 2: the initial Gloas block built with the parent block hash from the EMPTY branch of the validator guide is invalid; the same block built with the FULL branch is valid. The fork-choice half is shown by the text, not by execution.

Proposed correction

Add a short fork transition section to the fork-choice text: how existing store entries are converted, whether a Fulu block counts as FULL in Gloas fork choice (or a pre-Gloas exception in the validator guide), and one helper that returns the execution block hash of a block of either fork.
